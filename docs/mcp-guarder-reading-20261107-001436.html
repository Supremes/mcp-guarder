A

结论：这个项目值得怎样理解和汇报？

TLDR

这是“透明代理 + 分层检测 + 调用授权 + 结果脱敏 + 审计”的工程项目。 述职主线应是边界选择、工程取舍和证据质量，而不是堆功能或只报最高召回率。

从第一性原理看问题

模型会把工具定义当成上下文，而工具定义来自外部 Server。只有在定义进入上下文前设检查点，才有机会阻止描述投毒。调用发生后的权限确认不能替代这一检查。

工具结果又是另一条不可信输入通道。现有实现只对结果做 secret 脱敏，尚未识别其中的诱导指令。因此，“描述投毒检测”和“结果间接注入防护”必须分开讲。

B

架构深度：为什么检查点放在这里？

进程边界。 图中网关和上游是两个进程，不是两个函数。启用本地 LLM 时，模型服务也是额外进程。网关不是沙箱，上游仍继承宿主环境变量。

协议边界。 网关只深加工 tools/list 响应及 tools/call 请求、响应。其他方法保留原始行内容并转发。通知不会触发网关主动扫描；客户端重拉列表时才重新检查。

透明性的准确含义。 不经数据模型重建，能保留未知 JSON 字段。两条泵会移除输入行尾，再写入 LF；因此不是对任意换行格式的逐字节恒等承诺。

并发与生命周期不是附属细节

客户端方向由 daemon 线程阻塞读取。上游响应方向在主线程运行。id 账本、审计和两侧写出使用锁，避免并发写坏协议行。

LLM 分类同步占用响应泵。它节省了调度复杂度，但一次慢分类会推迟后续上游消息的处理。当前没有后台扫描队列。

POSIX 下，上游在独立进程组启动。客户端关闭输入后，网关先请求正常退出，再升级到终止信号。收尾还覆盖同一进程组中的孙进程。它不是对主动脱离进程组的进程提供隔离保证。

证据：proxy.py:359–376、proxy.py:429–640、proxy.py:647–695。

C

代码深度一：工具定义如何被留下或剥离？

顺序细节。 当前代码先对原列表做指纹检查，再对原列表做静态扫描。它不是“指纹剥离后，静态层就不再扫描”。跳过预剥离工具的是 LLM 阶段。

证据：proxy.py:1009–1092。任何检测器内部错误都会走空列表分支，见 proxy.py:1133–1160。

TOFU 记录的是历史基线，不是安全认证

默认摘要字段是 name/title/description/inputSchema。它们经 canonical JSON 生成 16 字节 blake2b 摘要。annotations 不在默认指纹字段中，但会被静态和语义检查。

状态 指纹库动作 对本次列表的意义
FIRST_SEEN 写基线并尝试保存快照 只表示首次见到；仍继续其他检测
UNCHANGED 更新最后出现时间 历史一致，不代表无毒
CHANGED 保存新快照，不覆盖旧基线 剥离；后续列表仍能识别该变化
人工 trust 运维命令接受新摘要 只更新指纹信任；不会撤销静态或语义规则

下面的“不更新基线”是 rug pull 防护的关键。若变化时自动覆盖基线，下次扫描就会把恶意版本视为正常。

证据：fingerprint.py:75–130、fingerprint.py:388–468；types.py:308–316。

静态规则分离“命中”与“处置”

31 条规则由 11 条 deny 和 20 条 warn 组成。每条规则的 on_hit 优先于段级默认值。自定义 rules 会替换整套内置规则，不是追加。

扫描会递归覆盖 schema 和 annotations 的字符串值及字典键。多个命中会全部收集；日志保留规则、字段路径和转义后的片段。

真正的工程判断。 合法的功能前置条件也常出现命令式句子。把所有宽泛命中设成 deny，会把可疑线索误当成安全结论。

证据：types.py:334–354；static_checks.py:44–165；proxy.py:1054–1080。

LLM 是受限分类器，不是另一个执行 Agent

请求包含工具定义、Server 名和同批上下文。定义用随机 nonce 标签包装。请求不授予执行工具，输出按索引对齐并校验 verdict。

nonce 和输出约束是防护措施，不是防注入证明。解析器检查核心结构，但会给缺失的 confidence/reason 补默认值，也会截断或钳制部分输出。不能把它描述为完整 JSON Schema 验证器。

成功判定缓存到 SQLite。缓存键为“prompt 版本 + model + 工具定义摘要”。不可用和非法输出不缓存，后续扫描会重试。

预算语义。 timeout_s 是一次判定列表的总预算，不是每批预算。默认总预算 20 秒，每批最多 16 个工具。超时后的工具进入 UNAVAILABLE；默认是告警放行。

上下文语义。 缓存键不含 Server 名、同级工具列表或端点地址。共享缓存时，分类上下文变化不会自动使旧判定失效。当前设计选择的是简单复用，而非完整上下文隔离。

证据：semantic.py:186–263、semantic.py:308–319、semantic.py:371–467；types.py:358–375。

D

代码深度二：一次调用如何被授权、改写和记账？

权限门是一套规则解释器

工具名按区分大小写的 glob 匹配。规则内条件是 AND。任何条件不满足，就尝试下一条规则。全部未匹配才默认拒绝。

六个操作符是 starts_with、equals、matches、not_matches、one_of、exists。除 exists 外，缺失参数都不匹配。allow: ask 当前等价于 deny。

两个容易误解的边界。 starts_with 做字符串前缀比较，不做文件真实路径解析。启动期冲突检查只拒绝相同 glob 字面量和重复 id，不分析不同 glob 的交集。

证据：policy.py:139–237；config.py:211–270。路径策略不是文件系统沙箱，重叠规则仍由顺序决定。

脱敏是局部改写，不是任意数据防泄漏

方向 默认检查范围 三类动作
出站 params.arguments 内字符串值 mask、drop_field、deny_call
回流 content[].text、内嵌 resource.text、structuredContent mask、drop_field；deny_call 降级为 mask
非目标 未配置字段、字符串键、编码或拆分后的 secret 不保证识别或改写

内置模式覆盖 AWS AKID、JWT、OpenAI key、GitHub PAT 和私钥块。命中区间先在原文上收集，再统一替换，避免替换文本被后续规则重复处理。

回流时上游调用已经发生。mask 可以阻止部分敏感内容继续返回，不能撤回上游副作用。

证据：redact.py:82–136、redact.py:147–244。

审计参与授权，但不是事务系统

获准调用先写审计，再转发上游。写入失败会阻断当前调用，并使后续调用进入拒绝状态。回流审计失败也返回工具错误，但此前的上游操作已经执行。

audit_id 用于追踪决策。rpc_id 关联请求响应，tool_use_id 可对齐客户端记录。每日 JSONL 与人工可读日志分开；fsync 策略决定持久化成本。

这不是跨文件和上游服务的原子事务。“写过 allow 日志”不等于“上游已成功执行”。结果应结合响应事件判断。

证据：proxy.py:899–946、proxy.py:1189–1275；audit.py:314–475。

列表剥离不等于调用禁用

当前调用路径不查询 tools/list 的剥离集合。 即使某工具已从列表移除，显式 allow 规则仍能放行后续直接调用。 报告中的“工具不可见”和“工具不可调用”必须分开陈述。

证据：proxy.py:768–946、proxy.py:1054–1134。本报告用隔离的进程内检查确认此边界，没有启动上游或执行描述中的指令。

现状差距：下一步应补什么证据与机制？

成熟度判断

建议把当前阶段定位为“核心闭环已实现，有离线效果证据”。 不要把 CLI 联调、有限样本零误报或功能存在，写成生产级安全保证。

按影响优先，而不是按功能数量排期

优先级 当前缺口 建议动作，不代表已实现 完成标准
高 LLM 预算耗尽时默认放行 先明确未知状态策略；评估显式 deny 或暂扣方案 未判定工具数量可观测；策略行为可解释
高 定义剥离与调用授权未联动 明确是否需要会话级禁用集合及恢复规则 对缓存工具名的调用有明确处置
高 result 只脱敏，不识别诱导 设计会话级污点策略，再做成对 Agent 实验 同时报攻击成功率、任务完成率和额外成本
中 真实正常数据来自单一 Server 在隔离环境导出更多 Server，冻结新留出集 每个 Server 的误报、失败和样本数可追溯
中 缓存忽略部分判定上下文 明确 model、端点及同级工具变更的失效策略 上下文变化不会无意复用不适用判定
后续 HTTP/SSE、OAuth 和交互审批缺失 在需求明确后扩展，不先堆 transport 身份边界、权限语义和客户端兼容有证据

“暂扣后后台扫描”只是技术文档中的候选方案。它会引入队列、状态及通知机制；当前最短路径是先定义未知状态的处置契约。

阅读旧文档时要校准的五句话

旧表达或易产生的理解 更准确的现状
“deny 层零误报” MCPTox 正常与 GitHub 样本为零；手写合法描述仍误报 1/30
“被剥离后调用按 no-match 拒绝” 是否拒绝仍取决于独立 policy；显式 allow 可继续放行
“任何异常都 fail-closed” 内部检测错误拒绝；模型不可用默认 warn；非调用审计失败不全面断流

述职内容示例：可以怎样讲，怎样回答追问？

开场摘要，适合项目简介

mcp-guarder 是一个透明的 MCP 安全网关。 它在工具定义进入模型上下文前做检查，并对调用实施权限控制、双向脱敏和审计。 项目已有离线分类证据，但不承诺全面防注入。 我的职责是［填写真实范围］。

约 3–5 分钟讲稿

背景与目标

这个项目解决的是工具接入中的信任边界问题。AI Agent 不仅会执行工具，也会读取 Server 提供的描述和 schema。恶意指令可以在调用发生之前进入上下文。

因此，项目选择在 MCP 传输层建立检查点。目标不是改造模型，而是在保持接入方式的同时，控制定义可见性、调用权限和结果中的敏感内容。

我在项目中负责［填写本人职责］。与我协作的部分是［填写合作边界］。以下成果中，我直接承担的是［列出具体交付］。

架构与实现

项目采用一个网关对应一个 Server 的 stdio wrapper。网关不使用高层数据模型重建全部消息。它只深加工工具列表和工具调用，其他协议字段尽量保持原状。

工程难点不只是写检测规则。还包括响应 id 关联、双向请求转发、子进程退出，以及日志不能污染协议输出。调用侧先脱敏，再求权限，最后写审计并决定是否转发。

定义检查采用三层互补机制。TOFU 识别已见定义的变化；高精确度规则直接剥离；宽泛规则只提供告警线索。可选 LLM 负责判断语义诱导。

一个重要取舍是没有把所有正则命中都视为攻击。合法工具也会要求先调用其他工具。为降低误拦，项目把“发现线索”和“自动阻断”明确分开。

结果与证据

历史离线评测中，本地 9B 量化模型在 207 条测试投毒样本里检出 195 条，召回约 94.2%。同一测试集的正常样本误报为 3/132。

当前规则的自动剥离层在全量数据上检出 101/485。全部规则命中为 470/485，但其中包括只告警的规则。这两个数字属于拟合口径，不能当作独立泛化结论。

除了效果数字，项目还交付了固定数据切分、实验摘要、逐样本记录和失效实验追踪。这使方案变化可以复盘，而不是只保留最好的一次结果。

价值与不足

当前已证明的价值，是把工具接入风险转化为可检查和可追溯的协议事件。部署规模、节省工时和实际攻击成功率变化，还需要补充业务与行为层证据。

我不会把“列表中不可见”直接说成“无法调用”。当前调用权限仍由独立 policy 决定。LLM 不可用时默认告警放行，也是必须明确说明的边界。

下一阶段建议优先解决未判定工具的处置，再补 result 注入策略和成对 Agent 实验。这样才能把离线分类能力推进为可证明的实际防护收益。

常见追问与回答要点

追问 建议回答
为什么不是只用客户端 hooks？ 本项目要在定义进入上下文前处理消息，也要改写结果。调用拦截不能替代这两个检查点。具体 hooks 能力仍取决于客户端版本。
为什么不用 MCP SDK？ 当前更重视未知字段保留，选择原始字典与行转发。代价是自行维护 id 和生命周期，不是 SDK 没有价值。
96.9% 是项目自动拦截率吗？ 不是。它是拟合数据上的全部规则命中率，包含 warn。自动剥离层是 101/485。
LLM 是否已经解决投毒？ 没有。测试集仍漏 12 条、误报 3 条。组合部署和 Agent 行为收益也未完成全量评测。
为什么不全交给 LLM？ 存在延迟、服务失败和分类不稳定。确定性规则、指纹和调用权限仍有独立价值。
审计是不是保证没有 secret？ 不是。调用载荷按配置脱敏，但原始定义快照和分类请求不具备无敏感信息保证。
你最重要的个人贡献是什么？ 只选择本人真实负责的一项决策，讲约束、替代方案、实现和证据。不要代领整个项目。
下一步怎么证明价值？ 用配对任务同时测攻击成功率、合法任务完成率、延迟和成本，并保留失败样本。
