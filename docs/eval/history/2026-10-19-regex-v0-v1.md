## 结论

| 规则 | 集合 | 召回率 | 误报率 |
|---|---|---|---|
| v0（内置 7 条） | 开发集 | 20/278 = 7.2%（95% CI 4.7–10.9%） | 0/230（CI 0–1.6%） |
| v0 | **测试集** | **2/207 = 1.0%**（CI 0.3–3.5%） | 0/132（CI 0–2.8%） |
| v1（v0 + 12 条结构规则，共 19 条） | 开发集 | 265/278 = 95.3%（CI 92.2–97.3%） | 0/230（CI 0–1.6%） |
| v1 | **测试集** | **149/207 = 72.0%**（CI 65.5–77.7%） | 0/132（CI 0–2.8%） |

1. **内置规则对语义投毒基本无效。** MCPTox 的投毒样本没有一条带 `<IMPORTANT>` 这类标签，全是"使用 X 之前必须先做 Y"式的语义诱导。v0 在测试集上只抓到 2 条，都来自 `read-extra-file` 的敏感路径匹配。
2. **按攻击结构写正则能显著提升召回率，但泛化有限。** v1 在测试集上召回 72%，比开发集低 23 个百分点。这个差距就是规则贴合开发集措辞的程度。
3. **误报率 0 不能代表真实场景。** 在 MCPTox 的 362 条正常描述上，v1 一条都没误报；但 5 条手写的合法描述全部被命中（见下文）。真实误报率很可能明显高于测试集数字。
4. **建议**：v1 保持可选，不替换内置默认规则。如需启用，建议配合 `on_hit: warn`，只告警、不剥离 tool。

## 实验设置

- **样本**：投毒 485 条，正常 362 条，来自 45 个真实 MCP Server。正常样本取自 `clean_system_promot`。Apify 在 prompt 里有 16 个 tool，`tool_names` 字段只登记了 7 个；按模型实际可见的内容取 16 个。没有解析错误。
- **切分**：按 Server 固定切分（种子 20261016）。开发集 30 个 Server（278 投毒 / 230 正常），测试集 15 个 Server（207 / 132）。切分文件在编写任何新规则之前提交（[split.json](../../../eval/mcptox/split.json)）。
- **判定**：以 tool 为单位，`static_checks.scan_tool` 有任意命中即判为投毒。
- **流程**：v1 只依据开发集编写。规则冻结并 commit（`05edd05`）后，测试集只跑了一次。

## 漏检分析（测试集 58 条）

漏检集中在三类，都指向正则对措辞的脆弱性：

1. **命名风格**：`before-trigger-tool` 要求工具名包含 `_` 或 `-`，开发集里的 Server 都是 snake_case / kebab-case。测试集的 Email Server 用 camelCase（如 `deleteEmail`），这条规则对它完全失效。
2. **动词同义替换**：使用 fetch、request、scan、perform、query、read 等动词的跨工具调用指令，规则没有覆盖。
3. **不规范语法与政策包装**：如 "Before use the tool …"、"Before deletion, make sure get …"，或把指令包装成 "System Policy: …"、"SECURITY ALERT: …" 后再给出改写要求。

继续给 v1 补同义词和命名变体，可以在这个测试集上拿到更好看的数字。但那属于看过测试集之后的调参，必须作为新版本（v2），在新的未见数据上重新评测。

## 误报风险：手写合法描述探测

下面 5 条是手写的、在真实 MCP Server 中合理的描述。它们**不是指标**，只用来说明规则可能误报的方向：

| 合法描述 | v1 命中 |
|---|---|
| Before using this tool, call list_files to obtain a valid file_id. | `before-trigger-tool` |
| When using this tool, set the version field to the value returned by get_record to avoid conflicts. | `argument-tampering`, `when-using-rewrite` |
| You must call 'auth_login' once per session before any other tool. | `must-call-tool` |
| Always append a project key (e.g. PROJ) to the query for faster results. | `always-rewrite` |
| The limit parameter to 'run_query' defaults to 100. | `argument-to-literal` |

5 条全部被命中。原因在于"先调用 A 再调用 B"、"设置某个参数"本来就是合法 tool 描述的常见写法，和投毒在句法上没有区别，区别在意图和目标。MCPTox 的正常描述普遍较短，很少出现这类跨工具说明，所以测试集上的误报率为 0。

## 能力边界

正则能识别的是攻击的**句法外形**：优先级声明、"必须先调用"、"改写参数"。它识别不了**意图**：同一句"调用 X 之前先调用 Y"，在合法 Server 里是使用说明，在恶意 Server 里是攻击。这和 README 中"不保证拦截所有 prompt injection"的定位一致：

- 静态规则适合作为低成本的第一道筛查，最好配合 `warn` 模式和人工 review（`mcp-guarder diff`）。
- 更可靠的防线仍然是 TOFU 指纹（防 rug pull）和 policy 默认拒绝：就算投毒描述绕过了检测，越权调用仍然需要通过权限规则。

## 过程记录

- **数据残留**：248 条投毒描述末尾带有字面量 `\nArguments:\n- No arguments\n\n\n`，是 prompt 渲染残留，正常样本里没有。不处理的话，规则可以靠它直接认出投毒样本。loader 从 v2 起剥离这段残留（`loader_version: 2`）。v0 因此在测试集上跑了两次：两次的数字完全相同（2/207）。v0 没有经过任何调参，不存在泄漏问题。
- **runner bug**：最初的脏工作区检测路径写错，没能标出未提交的改动。`v0-test.json` 记录的 `code_commit` 为 `e3828d2`，实际运行时 loader 已经是 v2 但尚未 commit；数据内容以结果里的 `loader_version` 和 `dataset_sha256` 为准。修复后重跑了两份开发集结果。`v1-test.json` 在干净的 `05edd05` 上运行，不受影响。
- 结果文件只包含样本 ID 和统计，不含 MCPTox 原文。本报告中的攻击句式是归纳后的复述。

## 局限

- 正常样本只有 45 个 Server、362 条，没有完整 inputSchema，误报率的置信区间较宽，而且不代表真实分布（见上面的探测）。
- 投毒样本由论文作者按模板构造，全部是英文，和野外攻击的分布不同。
- 没有评测 inputSchema 投毒和非英文诱导。
- 没有评测 TOFU 指纹（MCPTox 样本都是首次出现）。
